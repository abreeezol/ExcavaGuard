# 06 · 目标实现度评估：用户上传数据 → 确定性计算与风险识别

> 评估日期：2026-10-10
> 评估对象：目标「用户上传自有数据后，由现有 Agent 完成确定性计算与风险识别，并标注所采用的标准规范；
> 若用户同时上传新规范，则按用户规范执行」
> 评估方式：**代码路径核查 + 实测验证**（非文档推断）
> 结论一句话：**计算引擎与规范机制已经可用，但"用户上传"这一入口尚未打通 —— 原始观测表进不来，实测 100% 弃权。**

---

## 一、目标拆解为可验证条件

| 编号 | 验收条件 | 判定标准 |
|:--:|---|---|
| A | 用户能上传自有监测数据 | 存在通用读取通道（CSV/Excel → 内部结构），能容忍真实世界的列名/编码/单位差异 |
| B | 系统完成确定性计算 | 对用户数据产出累计值、本次变化量、变化速率、趋势斜率，且弃权率可接受 |
| C | 系统完成风险识别与分级 | 产出五级风险等级 + 问题类别 + 危险报警判定 |
| D | 标注所采用的标准与规范 | 每条结论可追溯到「规范名称 + 条文号 + 阈值来源」 |
| E | 用户上传规范时按其执行 | 用户阈值按字段覆盖默认库，结果标注实际生效来源 |

---

## 二、逐条评估

| 条件 | 状态 | 证据 | 差距 |
|:--:|:--:|---|---|
| **A 上传数据** | ❌ **未实现** | 8 个 Skill 全部只有 `SKILL.md` 骨架（无 `scripts/`）；`pipeline` 只接受 `list[dict]`；`tools/` 下的读取器都是**针对特定数据集写死的**，无通用用户上传通道 | 无 CSV/Excel 通用读取器；无列名映射；无编码探测；无上传入口 |
| **B 确定性计算** | ⚠️ **引擎可用，但用户数据进不来** | 四项计算已实现，126 项回归测试全绿；**但实测**：仅含 `point_id/timestamp/metric/value/unit` 的原始观测表 → **7/7 全部弃权**（`MISSING_BASELINE` + `MISSING_PREVIOUS`） | 见 P0-1：基准值/上次值/间隔被当作**输入字段**而非**时序派生量** |
| **C 风险识别** | ✅ **已实现** | 五级分级（正常/关注/预警/报警/危险报警/未知）+ 四类问题 + GB 50497-2019 §8.0.9 危险报警条件；27 个模拟场景 100% 通过 | 依赖 B，用户数据目前拿不到结论 |
| **D 标注规范** | ✅ **已实现** | 每条结论带 `evidence.standard` + `evidence.clause`；`effective_source` 含 `origin` / `origin_display` / `source_id` / `source_label` / `rule_id` / `overridden_fields`；`checks[].limit_basis` 给出限值推导过程 | 下游日报 Agent 需正确转述（已在 `04_日报模块接口契约.md` 约束） |
| **E 用户规范优先** | ⚠️ **机制可用，缺安全校验** | `resolve_limit` 中 `rank()` 令 `user_rank=1` 优先；`upload_standard()` 有格式校验；字段级覆盖并记录 `overridden_fields` | 见 P1-1：**不校验用户阈值是否比默认更宽松** |

**总体实现度：D、C 已达成；B 引擎达成但入口阻塞；A 未达成；E 机制达成但缺一道安全闸门。**

## 三、已实现的部分（有实测证据）

### 3.1 确定性计算引擎

| 能力 | 实现 | 验证 |
|---|---|---|
| 累计值 `current − baseline` | `calculator.cumulative_value()` | ✅ |
| 本次变化量 `current − previous` | `calculator.single_change_value()` | ✅ |
| 变化速率 `|Δ| / interval_days` | `calculator.rate_value()` | ✅ |
| 趋势斜率（最小二乘） | `calculator` + `build_point_series()` | ✅ |
| 输入不足即弃权，不猜不插补 | 6 个阶段二弃权码 | ✅ 实测弃权而非编造 |
| 单位按量纲换算（长度/压强/力/无量纲/温度） | `ingest.normalize_value_unit()` | ✅ |

### 3.2 风险识别

- 五级分级 + `未知`（弃权）严格区分；`未知` **不等于安全**（已写入 `AGENTS.md`）
- 问题类别：变形过大 / 渗漏水与地下水异常 / 支护受力异常 / 裂缝发展 / 数据质量异常 / 其他
- 累计值取 `min(绝对量, %H)`；速率「达到规定值 或 连续 3 次 > 70%」；底板浇筑后速率 ×0.7；
  位移不收敛（JGJ 120-2012 §8.2.23-2）；GB 50497-2019 §8.0.9 危险报警条件
- 高严重度数据质量问题**阻塞判定**并转人工复核（`DATA_QUALITY_BLOCKED`）

### 3.3 规范标注与用户上传

- 默认规范库：GB 50497-2019 条文级阈值，**22 项监测项**
- 用户上传：`upload_standard(payload, user_dir)` → 字段级合并 → `overridden_fields` 逐字段记录来源
- 用户未上传时**静默使用默认库**，不报错不告警（符合确认口径）

## 四、关键差距

### P0-1 · 原始观测表无法直接计算（已实测复现）★最严重

**实测**：

```python
# 用户最可能上传的形态：测点 / 时间 / 监测项目 / 数值 / 单位
raw = [{'point_id':'WTHD-01','timestamp':'2026-08-01','metric':'wall_top_horizontal_displacement',
        'value':0,'unit':'mm'}, ...]           # 共 7 期，累计 60 mm（远超限值 20 mm）

run_pipeline(raw, ctx)
# → 阶段二弃权 7/7
# → 弃权码 ['MISSING_BASELINE', 'MISSING_PREVIOUS']
# → 风险等级分布 {'未知': 7}        ← 零风险识别输出
```

补齐 `baseline_value` / `previous_value` / `interval_days` 后，同样数据得到
`{'未知': 1, '危险报警': 6}` —— **同一份数据，两种截然不同的结果**。

**根因**：这三个量在代码中被当作**输入字段**，而不是从时间序列**派生**的量。

```python
# orchestrator.compute_batch_with_series() 现状
compute(
    current  = r.value,
    baseline = r.baseline_value,      # ← 直接取输入，不推导
    previous = r.previous_value,      # ← 直接取输入，不推导
    interval_days = r.interval_days,  # ← 直接取输入，不推导
    history = hist,                   # ← 只有斜率用了序列
)
```

而 `build_point_series()` **已经把按测点排序的时间序列建好了**，只是没用于填充这三个量。

**影响**：直接阻断目标 B。用户上传得越"原始"，系统越拿不到结论；只有恰好自带这三列的数据才能算。

**修复方向**：在阶段一与阶段二之间插入「时序派生」步骤 ——
按 `point_id` 排序后，`baseline = 首期有效值`、`previous = 前一期有效值`、
`interval_days = 本期与上期有效观测的时间差`。**已有的 `build_point_series()` 可直接复用**，
改动集中在 `compute_batch_with_series()`。

### P0-2 · 没有用户数据接入通道

| 缺失项 | 现状 | 影响 |
|---|---|---|
| 通用 CSV / Excel 读取器 | 无。`tools/` 下的读取器全部针对特定数据集硬编码 | 用户上传的文件无法进入管线 |

| 编码探测 | 无。真实数据中已出现 `latin-1` 编码的 CSV | 直接读取会乱码 |
| 上传入口 | 无。`pipeline` 只接受 `list[dict]`，无 CLI、无接口 | 用户无从下手 |
| Skill 实体 | 8 个 Skill 全部只有 `SKILL.md` | `parse-monitoring-data` / `normalize-monitoring-data` 声明的能力没有实现 |

### P1-1 · 用户规范可能比默认更宽松，无安全校验

`resolve_limit()` 的选择逻辑：

```python
def rank(item):
    user_rank = 1 if any(o == ORIGIN_USER for o in origins.values()) else 0
    return (user_rank, spec)          # ← 只看"是否来自用户"，不看"是否更宽松"
```

**风险场景**：用户上传一份把「一级基坑墙顶水平位移累计限值」从 20 mm 放宽到 50 mm 的"企业标准"，
系统会**照用**，把本该判为「危险报警」的 35 mm 判成「预警」。

**现有缓解**：`overridden_fields` 会记录被覆盖的字段，`effective_source.origin = user_uploaded` 会标注来源。
**但没有任何机制提示"这条用户阈值比默认更宽松"**，使用者要自己比对才能发现。

**建议**：在 `upload_standard()` 或 `resolve_limit()` 中增加**严格度比对** ——
若用户限值严于默认，正常采用；若宽于默认，写入 `flags`（如 `USER_LIMIT_LOOSER_THAN_DEFAULT`）
并在结果中显著提示，必要时要求确认。这属于"工程安全边界"应覆盖的内容，目前 `AGENTS.md` 未涉及。

---

### P1-2 · 缺 H 时不弃权，改用绝对量限值（可能偏松）

```python
if abs_limit is not None and pct_limit is not None:
    lim.cumulative_mm = min(abs_limit, pct_limit)
elif abs_limit is not None:
    lim.cumulative_mm = abs_limit          # ← 只给绝对量，未做 min
```

GB 50497-2019 表 8.0.4 规定累计值取 `min(绝对量, %H)`。当未提供基坑设计深度 H 时，
系统退化为**只用绝对量限值**，仅留一个 `PCT_H_NOT_EVALUATED` 标记，**不弃权**。

| 场景 | 绝对量限值 | %H 限值 | 规范要求的限值 | 系统实际使用 | 偏差 |
|---|---:|---:|---:|---:|---|
| H = 20 m | 20 mm | 0.2%×20×10 = 40 mm | 20 mm | 20 mm | ✅ 一致 |
| H = 5 m | 20 mm | 0.2%×5×10 = 10 mm | 10 mm | **20 mm** | ❌ **偏松 100%** |

**附带发现**：`MISSING_H` 弃权码在 `ABSTAIN_REASONS` 中**已定义但全项目从未被使用**（死代码），
说明"缺 H 应弃权"的设计意图没有落地。

---

### P1-3 · 工程条件必须由调用方提供，无交互补全

`safety_level` / `support_type` / `excavation_depth_m` / `design_values` 全部由调用方传入
（见 `ProjectContext`）。用户上传监测数据时不会自带这些，缺失时系统弃权
（`MISSING_DESIGN_VALUE`、`NO_APPLICABLE_RULE` 等），但：

- 用户不知道**为什么**弃权、**该补什么**；
- 没有"缺什么就提示补什么"的交互回路。

---

### P2-1 · 温度补偿未实现

`observations.csv` 含 2,951 条温度记录（12.8~21.4 ℃）。支撑/锚杆轴力的变化量中会混入温度效应，
当前阶段二**不做温度补偿**，可能高估轴力类风险等级。

### P2-2 · 没有一例完整的真实基坑监测数据

`01_数据清单与可用性评估.md` 的结论：现有 3 个数据集**没有任何一个**同时满足
「基坑监测项 + 日频时序 + 基坑设计深度 H + 安全等级 + 支护形式」。
因此"用户上传数据"这条链路**目前没有真实样例可做端到端验证**，
只能靠模拟数据 + 手工构造的样例回归。

## 五、风险点汇总

| # | 风险 | 触发条件 | 后果 | 现有缓解 | 缺口 |
|:--:|---|---|---|---|---|
| R1 | **用户上传原始数据后零输出** | 数据不含 `baseline_value`/`previous_value`/`interval_days` | 全部弃权，用户以为"系统没能力" | 无 | **P0-1 时序派生** |
| R2 | **用户上传宽松规范导致漏判** | 用户规范限值宽于默认 | 危险判为正常，**安全事故风险** | 标注 `overridden_fields` / `origin` | **P1-1 严格度校验** |
| R3 | **缺 H 时限值偏松** | 未提供 `excavation_depth_m` | 浅基坑限值可能放宽一倍 | `PCT_H_NOT_EVALUATED` 标记 | **P1-2 应弃权或要求补 H** |
| R4 | 规范阈值取自扫描版 PDF | 使用默认规范库 | 管线/道路数值可能与纸质规范有出入 | 文档已标注"须设计方复核" | 需人工核对纸质规范 |
| R5 | 用户数据被误标来源 | `data_origin` 未正确设置 | 真实/模拟统计混同 | 默认 `real`，非法值记 `UNKNOWN_DATA_ORIGIN` | 需在接入层强制确认 |
| R6 | `未知` 被下游误读为"安全" | 日报 Agent 未遵守契约 | 弃权项被渲染为正常 | `AGENTS.md` 已约束；契约已声明 | 下游实现时需复查 |
| R7 | 无真实基坑数据可验证 | 端到端验收 | 上线后才发现问题 | 27 个模拟场景覆盖 | 需真实数据或高质量仿真 |

## 六、建议推进顺序

| 优先级 | 事项 | 理由 | 预估改动范围 |
|:--:|---|---|---|
| **1** | **P0-1 时序派生**：由 `point_id` 排序推导 `baseline` / `previous` / `interval_days` | 直接解除目标 B 的阻塞；`build_point_series()` 已就绪，改动集中 | `orchestrator.compute_batch_with_series()` + 测试 |
| **2** | **P1-2 缺 H 行为**：改为弃权 `MISSING_H`，或至少显著降级 | 消除一个会"放宽判据"的隐患；`MISSING_H` 码已存在 | `risk_identifier.resolve_limit()` |
| **3** | **P1-1 规范严格度校验**：用户阈值宽于默认时告警 | 消除 R2 这个最严重的工程安全风险 | `upload_standard()` / `resolve_limit()` |
| **4** | **P0-2 接入通道**：通用 CSV/Excel 读取器 + 列名映射 + 编码探测 | 打通目标 A；建议同步填充 `parse-monitoring-data` / `normalize-monitoring-data` 两个 Skill | 新增 Skill `scripts/` |
| **5** | P1-3 工程条件交互补全 | 提升可用性 | Agent 编排层 |
| **6** | P2-1 温度补偿 | 提升轴力类判据准确度 | `calculator` / `risk_identifier` |

**推荐先做 1 + 2 + 3**：这三项都在确定性计算层内部，改动可控、可测试，且直接决定
"用户上传数据后能否得到正确结论"与"结论会不会偏松"。做完之后，即使没有前端入口，
也能用 Python API 端到端跑通「用户数据 → 计算 → 风险识别 → 规范标注」。
