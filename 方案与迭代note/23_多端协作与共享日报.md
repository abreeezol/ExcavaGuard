# 多端协作与共享日报

## 范围与流程

同一工程的成员使用各自账号登录同一个 Next.js 服务。上传者提供监测文件，成员可从共享文件列表选择一份或多份数据生成一份日报；复核工程师在另一端打开同一运行，暂存逐项评价，再提交整份草稿决定。上传者看到相同的评价、复核状态和三件套下载。

- 沿用项目成员权限与 Supabase/local 双 Provider；不另建身份系统。
- 工作台共享列表支持报告日期与待复核筛选；每 15 秒及重新进入页面时刷新列表。
- 当前运行有新 revision 时提示更新，显式加载后再编辑，避免自动刷新覆盖未保存输入。
- 文件记录上传者，运行冻结生成者及全部输入文件清单，评价记录实际填写人，最终决定记录提交人。
- 暂存是当前草稿的共享评价，不是正式决定；以 revision CAS 合并本次条目，旧版本返回 409。
- 接受仍要求全部已判定非正常风险均有评价且无异议，未知仍按原责任边界处理。

## 统一日报的数据口径

统一日报基于用户明确选择的原始上传文件生成一个新运行，不拼接既有报告或重复汇总重跑结果。每份文件校验项目、大小和哈希；最多 10 份、合计 100 MB。单文件请求保持兼容。

多文件先使用现有 Python 读取器和归一化器核对通道，再把原始记录送入既有三阶段流程。跨文件同点同测项的量值语义、来源类别或长/宽表布局不一致时拒绝；归一化后相同通道、时间的跨文件观测重复时拒绝，由用户选定可靠来源。宽表先合并同通道历史，再按原每日末值规则聚合。长表不改变原单文件统计口径。保留区间前历史用于基准和前值推导，不重新归零。

共享日报始终是一份可追溯草稿；评价不修改冻结引擎事实或已审计文件。正式审核、预警与签发由工程师负责。

## 存储与部署

- 新字段为可选扩展，旧运行与旧文件保持可读，不伪造旧上传者。
- Supabase 文件表新增可空 `uploaded_by` JSON 列，迁移见 `202611020001_collaboration.sql`。账号仍使用单服务私有目录，不能将其误写入引用 Supabase Auth 的成员表。
- 真实异地访问需要共享服务地址，开发验证可用两个独立浏览器会话。服务端密钥留在服务器。
- 单服务必须持久化账号目录、项目补充规范 SQLite 和运行所需资产；仅共享 Supabase 不代表多台独立服务已共享这些本地目录。
- 本轮不添加自动签发、自动汇总全部历史或定时报送。

## 验证

已执行：Vitest 150项通过、6项外部服务测试默认跳过；多周期原生回归13项通过。两个独立Chrome会话验证同一报告共享，复核端接受后上传端自动看到新状态及加载提示；暂存保留评价和总评，上传端无复核表单。390px视口页面宽度仍为390px，无横向溢出。

防御性检查修正：共享接口响应使用契约解析；同时间戳运行历史以revision和run_id稳定排序；输入清单与生成者不可修改；保存未变化的评价不覆盖原填写人；409及自动同步不自动替换未保存内容，显式刷新提示确认。

生产构建通过，新增评价API已生成。新增云端历史摘要投影与旧文件列表经真实只读查询验证通过；该结果只证明现有资产仍可读取，不代替新增上传者字段的迁移及云端写入验收。
