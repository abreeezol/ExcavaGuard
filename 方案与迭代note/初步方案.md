# ExcavaGuard：AI 基坑监测日报智能体初步方案

## 一、项目定位

面向基坑监测工程师，自动读取当日监测数据和施工工况记录，依据适用规范完成确定性计算、异常筛查、证据检索和辅助归因，生成可复核、可追溯的监测日报草稿。

系统定位为工程师的辅助工具，不替代工程师承担安全判断、预警发布和报告签发责任。

## 二、总体判断

采用 `Skill + RAG` 的总体方向合理，但不宜把系统设计成多个大模型 Agent 共同投票作出安全结论。主交付采用独立 Web 多智能体应用，多个 Agent 作为单一应用中的逻辑角色协作：

> Next.js Web 应用 + Supervisor 与专业 Agent + 可测试 Skill 工具链 + 双知识库 RAG + 确定性规则引擎 + 人工签发

核心原则是：

- 规则主判：数值计算和阈值判断全部由确定性程序完成。
- RAG 举证：规范与案例知识库只提供可追溯证据。
- 模型表达：大模型负责受约束的解释和文字组织，不修改计算事实。
- 主动弃权：证据不足时明确提示信息不足，不强行归因。
- 人工闭环：正式预警、审核和签发始终由工程师完成。

## 三、能力边界

| 任务 | 推荐实现 |
| --- | --- |
| CSV 解析 | 数据接入 Skill |
| 点号、单位、方向统一 | 数据标准化 Skill |
| 累计值、变化量、变化速率计算 | 确定性规则引擎 |
| 超限判定 | 确定性规则引擎 |
| 规范条文查询 | 规范 RAG |
| 历史案例匹配 | 案例 RAG |
| 工况与异常关联 | 归因 Skill |
| 日报生成 | 模板化报告 Skill |
| 语言解释 | 受约束的 LLM |
| 正式预警与报告签发 | 工程师 |

特别需要明确：

```text
是否超限 = 规则代码计算
为什么这样判 = 规范 RAG 提供条文证据
可能由什么引起 = 案例 RAG 与工况规则提供参考
如何写进日报 = 大模型受约束生成
```

历史案例只能影响归因结论及其可信度，不能改变规范阈值和超限事实。

## 四、推荐架构

### 4.1 主流程

```text
监测数据与工况记录
        ↓
数据接入与标准化 Skill
        ↓
确定性规则引擎
        ↓
结构化事实表
        ↓
规范证据检索 + 案例检索 + 工况归因
        ↓
日报模板渲染
        ↓
数字、引用和字段一致性校验
        ↓
工程师复核与签发
```

### 4.2 建议的 Skill

- `parse-monitoring-data`：解析 MVP 的 CSV 输入，识别字段、单位和日期。
- `normalize-monitoring-data`：统一点号、方向、单位和缺失值表示。
- `evaluate-thresholds`：计算三重判据并输出结构化结论。
- `retrieve-standard-evidence`：检索规范条文及其适用条件。
- `retrieve-similar-cases`：检索相似工程和相似工况案例。
- `analyze-work-condition`：依据时间窗、空间窗、量级和方向做辅助归因。
- `render-daily-report`：按照固定模板生成日报草稿。
- `validate-report`：校验数字、引用、字段和模板完整性。

每个 Skill 都应具有稳定的输入输出结构、异常码和独立测试用例。

### 4.3 Agent 设置

初版采用一个 Supervisor 和五个专业 Agent：

- `Supervisor Agent`：维护共享状态，决定下一阶段，控制重试、退回、终止和人工确认；
- `数据治理 Agent`：调用解析与标准化 Skill，决定数据能否进入分析；
- `判据与规范 Agent`：绑定确定性计算事实、规则和规范证据；
- `风险归因 Agent`：检索案例并形成带反证、限制和可信等级的候选解释；
- `报告交付 Agent`：只使用结构化事实与证据生成日报草稿；
- `审计 Agent`：独立检查数字、引用、适用性和责任措辞，并将问题退回责任 Agent。

这些 Agent 是单一 Web 应用进程中的逻辑角色，可以使用同一个模型供应商，但必须拥有独立职责、提示词、工具白名单、结构化输入输出和终止条件。多 Agent 的价值来自规划、执行、审计、退回和人工接管闭环，而不是模型数量。

规范检索和案例检索仍作为可测试的 Skill，不让多个 Agent 通过投票改变规则引擎事实。安全关键的强制顺序、最大重试次数和停止条件由显式状态图控制。

### 4.4 Web 应用与运行时

主交付是独立 Web 应用，不要求评委安装 Codex、TRAE 或 WorkBuddy。Web 界面提供：

- 对话式任务入口与 CSV、工况文件上传；
- Agent 当前阶段、Skill 调用和错误状态；
- 测点计算过程、规范证据、案例差异和归因限制；
- 审计退回、人工确认和主动弃权记录；
- 日报草稿预览与导出。

服务端维护结构化工程状态，而不是只保存聊天消息。LLM、数据库、对象存储和向量库均由服务端访问，浏览器不得持有模型或数据库管理密钥。

WorkBuddy 专家、企业智能体或 MCP 适配只在 Web 主链路稳定后增加，并复用相同的 Skill、规则和 RAG 能力，不复制业务逻辑。

规范检索通过统一服务端接口连接不同 Provider。Pinecone 是默认托管方向，本地 BGE + ChromaDB 可作为可选离线 Provider；二者复用同一证据 Schema、Skill 和 Agent 链路，不实现两套业务逻辑。离线 Provider 可以由本机 sidecar 提供 HTTP 服务，但它不是 Web 主链路的必选后端，相关模型和知识库制品不进入主代码仓。

## 五、RAG 设计

### 5.1 规范知识库

规范库应按条文组织，不应只把整份规范切片后进行纯向量检索。每个知识单元至少保存：

- 规范名称；
- 规范版本；
- 条文号；
- 条文原文；
- 监测项目；
- 适用的基坑等级或工程条件；
- 地区与适用范围；
- 页码或来源定位；
- 生效和失效状态。

建议检索链路：

1. 按规范版本、监测项目和适用条件做元数据过滤；
2. 使用 BM25 进行关键词召回；
3. 使用向量检索补充语义召回；
4. 对候选条文进行 rerank；
5. 返回条文原文、条文号、版本和适用范围。

### 5.2 案例知识库

案例库优先保存结构化特征：

- 开挖深度；
- 支护形式；
- 土层条件；
- 地下水情况；
- 施工阶段；
- 监测类型；
- 异常方向；
- 变化速率；
- 已知工况事件；
- 事故或处置结果；
- 数据来源及可信等级。

检索时先进行结构化过滤，再对文本描述或响应曲线特征进行相似检索。匹配结果只能作为经验参考，并需要输出匹配条件、差异项和可信度。

## 六、可靠性设计

### 6.1 数字与语言分离

大模型不得直接计算累计值、变化量、变化速率或阈值。报告中的所有数字均来自结构化事实表。

### 6.2 强制证据

每条规范性判断必须关联：

- 规则 ID；
- 规范名称与版本；
- 条文号；
- 输入字段；
- 计算过程；
- 结论。

### 6.3 一致性校验

报告导出前逐字段比对：

- 报告数字是否与计算结果一致；
- 超限状态是否与规则引擎一致；
- 引用条文是否存在；
- 引用条文是否适用于当前监测项；
- 必填字段是否完整；
- 是否出现未经授权的自动预警措辞。

任何关键校验失败均拒绝输出正式报告，只允许生成错误清单。

### 6.4 弃权机制

以下情况应输出“信息不足，建议人工复核”：

- 工况记录缺失；
- 未找到适用规范条文；
- 案例匹配度不足；
- 多个证据相互冲突；
- 数据质量不满足分析条件；
- 异常变化无法被现有工况解释。

### 6.5 人工责任边界

- 系统只生成监测日报草稿；
- 系统不自动签字；
- 系统不自动对外发布预警；
- 工程师完成审核、修订和签发；
- 所有人工修改均保留审计记录。

## 七、演示版 MVP

初赛 Demo 聚焦一条完整、稳定、可解释的链路：

1. 上传一份当日监测 CSV 和一份施工工况记录。
2. 系统识别字段、单位、方向和异常数据。
3. 规则引擎完成三重判据计算。
4. 页面展示超限测点、输入值、阈值和计算过程。
5. 点击结论查看对应规范条文。
6. 对报警点给出工况归因、证据和可信度。
7. 无法归因时显示“信息不足，建议人工复核”。
8. 一键生成固定格式的监测日报草稿。
9. 通过一致性校验后允许导出。

可在现场增加一个故障演示：人为篡改报告数字或输入不合法单位，系统拒绝导出并指出不一致位置。这能够直观体现系统区别于普通大模型总结工具的可靠性。

## 八、初步技术选型

| 层级 | 初步选型 |
| --- | --- |
| Web 全栈 | Next.js + TypeScript |
| 服务端接口 | Next.js Route Handlers，MVP 不拆独立后端 |
| LLM 接入与流式输出 | Vercel AI SDK 或等价服务端适配层 |
| Agent 编排 | LangGraph.js；首条链路可先使用同契约的显式 TypeScript 状态机 |
| 数据契约 | Zod |
| 数据处理与规则引擎 | TypeScript 确定性模块 + 配置化演示阈值 |
| 结构化存储 | Supabase PostgreSQL |
| 文件存储 | Supabase Storage |
| 向量检索 | 统一检索接口；Pinecone 托管 Provider + 可选本地 RAG Provider |
| 关键词检索 | BM25 或等价关键词召回，按数据规模分阶段接入 |
| 报告生成 | `docx` 生成 DOCX，PDF 作为后续能力 |
| 测试 | Vitest |
| 主交付 | 可独立访问的 Web 应用 + 完整代码仓库 |
| 平台适配 | 主链路完成后增加 WorkBuddy 专家、企业智能体或 MCP |

初始化工程已固定 Next.js 16.4.0、React 19.3.0、TypeScript 6.0.3 与 Zod 4.6.5；完整依赖以 `package-lock.json` 为准。LLM、Embedding、rerank 模型、LangGraph.js 接入时机与部署平台仍待后续实现时确认。

本方案不再承诺“纯静态、完全离线、双击即用”。远程 LLM、Pinecone 或 Supabase 不可用时，系统只允许降级执行本地确定性计算与基础模板草稿，不能伪装成完整 RAG 和多 Agent 分析已经成功。

## 九、评测方案

### 9.1 核心指标

| 指标 | 说明 |
| --- | --- |
| 阈值计算正确率 | 与人工计算或金标准程序逐项比对，目标 100% |
| 报告数字一致率 | 报告与结构化事实表逐字段比对，目标 100% |
| 异常检出率 | 基于带真值标签的测试集统计 |
| 条文引用准确率 | 由土木专业人员审核引用是否正确且适用 |
| 无依据归因率 | 统计缺乏证据却给出确定归因的比例 |
| 弃权准确率 | 统计应弃权场景是否正确拒答 |
| 日报生成时间 | 与人工流程进行对照测试 |
| 人工修改率 | 统计工程师最终修改的字段比例 |

### 9.2 测试数据分层

- 正常数据；
- 单项超限数据；
- 多项复合超限数据；
- 单位错误数据；
- 方向相反数据；
- 缺失字段数据；
- 重复测点数据；
- 工况缺失数据；
- 规范适用条件冲突数据；
- 无相似案例数据。

时间节省、人工成本和准确率应通过对照实验获得，不宜提前填写未经验证的具体数字。

## 十、风险与待确认项

- 需要土木专业人员确认 GB 50497-2019 及地方标准的具体适用范围。
- “法定格式”建议改写为“依据规范附录表式生成日报草稿”。
- 需要确认规范全文、工程案例和项目数据的授权边界。
- 不同项目的监测报警值可能来自专项方案，不能只依赖统一国标阈值。
- 合成数据必须明确标注，不能与真实工程数据混用。
- 应验证案例相似度与实际归因可信度之间是否存在可靠关系。
- Web 托管环境的执行时限、流式连接和长任务恢复能力需要验证；若 Route Handler 不足，再引入任务队列，不在 MVP 前置建设。
- Pinecone、Supabase 与 LLM API 的网络可用性会影响完整演示，需要准备已脱敏的固定样例和明确降级状态。

## 十一、项目亮点表达

建议将项目的核心技术亮点概括为：

> 以确定性规则引擎承担安全判定，以 Skill 封装数据处理和报告生成，以双知识库 RAG 提供规范与案例证据，由 Supervisor 和专业 Agent 形成可见的执行、审计与退回闭环，并由工程师最终复核签发。

对外展示时重点强调：

- 规则主判；
- 证据可追溯；
- 数字零幻觉；
- 信息不足主动弃权；
- 模板化合规输出；
- 断网时仍可生成基础日报；
- 可替换规范库、测项契约和报告模板，迁移到隧道、边坡、高支模等场景。
