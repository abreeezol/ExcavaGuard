# ExcavaGuard：AI 基坑监测日报智能体初步方案

## 一、项目定位

面向基坑监测工程师，自动读取当日监测数据和施工工况记录，依据适用规范完成确定性计算、异常筛查、证据检索和辅助归因，生成可复核、可追溯的监测日报草稿。

系统定位为工程师的辅助工具，不替代工程师承担安全判断、预警发布和报告签发责任。

## 二、总体判断

采用 `Skill + RAG` 的总体方向合理，但不宜把系统设计成多个大模型 Agent 共同作出安全结论。建议采用以下技术框架：

> 单编排 Agent + 可测试 Skill 工具链 + 双知识库 RAG + 确定性规则引擎 + 人工签发

核心原则是：

- 规则主判：数值计算和阈值判断全部由确定性程序完成。
- RAG 举证：规范与案例知识库只提供可追溯证据。
- 模型表达：大模型负责受约束的解释和文字组织，不修改计算事实。
- 主动弃权：证据不足时明确提示信息不足，不强行归因。
- 人工闭环：正式预警、审核和签发始终由工程师完成。

## 三、能力边界

| 任务 | 推荐实现 |
| --- | --- |
| CSV/Excel 解析 | 数据接入 Skill |
| 点号、单位、方向统一 | 数据标准化 Skill |
| 累计值、变化量、变化速率计算 | 确定性规则引擎 |
| 超限判定 | 确定性规则引擎 |
| 规范条文查询 | 规范 RAG |
| 历史案例匹配 | 案例 RAG |
| 工况与异常关联 | 归因 Skill |
| 日报生成 | 模板化报告 Skill |
| 语言解释 | 受约束的 LLM |
| 正式预警与报告签发 | 工程师 |

特别需要明确：

```text
是否超限 = 规则代码计算
为什么这样判 = 规范 RAG 提供条文证据
可能由什么引起 = 案例 RAG 与工况规则提供参考
如何写进日报 = 大模型受约束生成
```

历史案例只能影响归因结论及其可信度，不能改变规范阈值和超限事实。

## 四、推荐架构

### 4.1 主流程

```text
监测数据与工况记录
        ↓
数据接入与标准化 Skill
        ↓
确定性规则引擎
        ↓
结构化事实表
        ↓
规范证据检索 + 案例检索 + 工况归因
        ↓
日报模板渲染
        ↓
数字、引用和字段一致性校验
        ↓
工程师复核与签发
```

### 4.2 建议的 Skill

- `parse_monitoring_data`：解析 CSV/Excel，识别字段、单位和日期。
- `normalize_monitoring_data`：统一点号、方向、单位和缺失值表示。
- `evaluate_thresholds`：计算三重判据并输出结构化结论。
- `retrieve_standard_evidence`：检索规范条文及其适用条件。
- `retrieve_similar_cases`：检索相似工程和相似工况案例。
- `analyze_work_condition`：依据时间窗、空间窗、量级和方向做辅助归因。
- `render_daily_report`：按照固定模板生成日报草稿。
- `validate_report`：校验数字、引用、字段和模板完整性。

每个 Skill 都应具有稳定的输入输出结构、异常码和独立测试用例。

### 4.3 Agent 设置

初版只保留一个流程编排 Agent，负责：

- 判断下一步调用哪个 Skill；
- 汇总各模块返回的结构化结果；
- 根据证据强度选择表述级别；
- 在证据不足时触发弃权；
- 组织最终报告说明文字。

不建议初期设置“国标 Agent、案例 Agent、复合 Agent”三个并列 Agent。多 Agent 会增加冲突处理、延迟、成本和调试复杂度，但未必提升安全性。规范检索和案例检索更适合设计为可测试的工具模块。

## 五、RAG 设计

### 5.1 规范知识库

规范库应按条文组织，不应只把整份规范切片后进行纯向量检索。每个知识单元至少保存：

- 规范名称；
- 规范版本；
- 条文号；
- 条文原文；
- 监测项目；
- 适用的基坑等级或工程条件；
- 地区与适用范围；
- 页码或来源定位；
- 生效和失效状态。

建议检索链路：

1. 按规范版本、监测项目和适用条件做元数据过滤；
2. 使用 BM25 进行关键词召回；
3. 使用向量检索补充语义召回；
4. 对候选条文进行 rerank；
5. 返回条文原文、条文号、版本和适用范围。

### 5.2 案例知识库

案例库优先保存结构化特征：

- 开挖深度；
- 支护形式；
- 土层条件；
- 地下水情况；
- 施工阶段；
- 监测类型；
- 异常方向；
- 变化速率；
- 已知工况事件；
- 事故或处置结果；
- 数据来源及可信等级。

检索时先进行结构化过滤，再对文本描述或响应曲线特征进行相似检索。匹配结果只能作为经验参考，并需要输出匹配条件、差异项和可信度。

## 六、可靠性设计

### 6.1 数字与语言分离

大模型不得直接计算累计值、变化量、变化速率或阈值。报告中的所有数字均来自结构化事实表。

### 6.2 强制证据

每条规范性判断必须关联：

- 规则 ID；
- 规范名称与版本；
- 条文号；
- 输入字段；
- 计算过程；
- 结论。

### 6.3 一致性校验

报告导出前逐字段比对：

- 报告数字是否与计算结果一致；
- 超限状态是否与规则引擎一致；
- 引用条文是否存在；
- 引用条文是否适用于当前监测项；
- 必填字段是否完整；
- 是否出现未经授权的自动预警措辞。

任何关键校验失败均拒绝输出正式报告，只允许生成错误清单。

### 6.4 弃权机制

以下情况应输出“信息不足，建议人工复核”：

- 工况记录缺失；
- 未找到适用规范条文；
- 案例匹配度不足；
- 多个证据相互冲突；
- 数据质量不满足分析条件；
- 异常变化无法被现有工况解释。

### 6.5 人工责任边界

- 系统只生成监测日报草稿；
- 系统不自动签字；
- 系统不自动对外发布预警；
- 工程师完成审核、修订和签发；
- 所有人工修改均保留审计记录。

## 七、演示版 MVP

初赛 Demo 聚焦一条完整、稳定、可解释的链路：

1. 上传一份当日监测 CSV 和一份施工工况记录。
2. 系统识别字段、单位、方向和异常数据。
3. 规则引擎完成三重判据计算。
4. 页面展示超限测点、输入值、阈值和计算过程。
5. 点击结论查看对应规范条文。
6. 对报警点给出工况归因、证据和可信度。
7. 无法归因时显示“信息不足，建议人工复核”。
8. 一键生成固定格式的监测日报草稿。
9. 通过一致性校验后允许导出。

可在现场增加一个故障演示：人为篡改报告数字或输入不合法单位，系统拒绝导出并指出不一致位置。这能够直观体现系统区别于普通大模型总结工具的可靠性。

## 八、初步技术选型

| 层级 | 初步选型 |
| --- | --- |
| 前端 | React 或 Vue |
| 本地后端 | Python FastAPI |
| 数据处理 | pandas、openpyxl |
| 规则引擎 | Python 规则模块 + 配置化阈值 |
| 结构化存储 | SQLite |
| 向量检索 | FAISS 或 Qdrant Local |
| 关键词检索 | BM25 |
| 报告生成 | DOCX/PDF 模板渲染 |
| 运行方式 | Docker 或一键启动脚本 |
| 桌面封装 | 后续按需采用 Electron/Tauri |

初赛不必把“纯静态、完全离线、双击即用”作为强约束。优先保证链路完整、结果稳定和演示可复现；桌面封装可以放在后续阶段。

## 九、评测方案

### 9.1 核心指标

| 指标 | 说明 |
| --- | --- |
| 阈值计算正确率 | 与人工计算或金标准程序逐项比对，目标 100% |
| 报告数字一致率 | 报告与结构化事实表逐字段比对，目标 100% |
| 异常检出率 | 基于带真值标签的测试集统计 |
| 条文引用准确率 | 由土木专业人员审核引用是否正确且适用 |
| 无依据归因率 | 统计缺乏证据却给出确定归因的比例 |
| 弃权准确率 | 统计应弃权场景是否正确拒答 |
| 日报生成时间 | 与人工流程进行对照测试 |
| 人工修改率 | 统计工程师最终修改的字段比例 |

### 9.2 测试数据分层

- 正常数据；
- 单项超限数据；
- 多项复合超限数据；
- 单位错误数据；
- 方向相反数据；
- 缺失字段数据；
- 重复测点数据；
- 工况缺失数据；
- 规范适用条件冲突数据；
- 无相似案例数据。

时间节省、人工成本和准确率应通过对照实验获得，不宜提前填写未经验证的具体数字。

## 十、风险与待确认项

- 需要土木专业人员确认 GB 50497-2019 及地方标准的具体适用范围。
- “法定格式”建议改写为“依据规范附录表式生成日报草稿”。
- 需要确认规范全文、工程案例和项目数据的授权边界。
- 不同项目的监测报警值可能来自专项方案，不能只依赖统一国标阈值。
- 合成数据必须明确标注，不能与真实工程数据混用。
- 应验证案例相似度与实际归因可信度之间是否存在可靠关系。
- 离线模型和本地知识库的体积、速度及部署方式需要单独测试。

## 十一、项目亮点表达

建议将项目的核心技术亮点概括为：

> 以确定性规则引擎承担安全判定，以 Skill 封装数据处理和报告生成，以双知识库 RAG 提供规范与案例证据，由单一编排 Agent 生成可追溯的日报草稿，并由工程师最终复核签发。

对外展示时重点强调：

- 规则主判；
- 证据可追溯；
- 数字零幻觉；
- 信息不足主动弃权；
- 模板化合规输出；
- 断网时仍可生成基础日报；
- 可替换规范库、测项契约和报告模板，迁移到隧道、边坡、高支模等场景。

## 十二、下一步

1. 明确一份最小输入数据契约。
2. 固化三重判据及其规则来源。
3. 制作 10 至 20 个带真值的演示测试案例。
4. 实现数据解析、规则判断和报告生成三项基础 Skill。
5. 建设最小规范知识库并验证引用准确率。
6. 增加案例检索和辅助归因。
7. 完成一致性校验、弃权和审计机制。
8. 使用真实操作流程测量效率提升与人工修改率。
