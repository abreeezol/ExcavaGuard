# 工程师风险评价闭环

## 一、目标与边界

报告通过独立审计后，复核工程师需要对系统已经形成确定性结论的非正常风险逐项评价，
再提交整份草稿的接受、退回或拒绝决定。评价用于留下人工判断、跟踪要求和异议证据，
不修改冻结监测事实、确定性风险等级、规范依据或报告文件。

评价对象为冻结载荷 `items` 中风险等级为「关注 / 预警 / 报警 / 危险报警」的条目。
「正常」无需逐项评价；「未知」表示系统弃权，仍进入原待人工复核队列，通过补充数据、
核对判据或建立关联运行处理，不能在评价入口中改写为已判定风险。

## 二、评价结构

每条评价绑定当前冻结风险条目的数组位置及以下事实快照：

- 测点编号；
- 监测项键名和名称；
- 观测时间；
- 系统风险等级；
- 工程师处置结论；
- 工程师说明。

处置结论分为：

- `confirmed`：确认风险结论；
- `follow_up_required`：确认并持续跟踪；
- `disputed`：对风险结论有异议。

接受当前草稿前必须覆盖全部评价对象，且不能存在 `disputed`。有异议时应选择退回修改，
保留已填写的逐项评价和总评，核对输入后建立关联运行。退回或拒绝允许只提交已完成的
评价，不要求为错误草稿补齐全部条目。

## 三、数据与权限

评价随现有 `POST /api/runs/:id/review` 一次提交，继续使用：

- 当前 `expected_revision`；
- 完整 `draft_ref`；
- 项目 `admin / reviewer` 权限；
- 本地或 Supabase 的不可变运行 revision；
- 并发版本冲突和草稿哈希校验。

服务端不信任浏览器提交的测点、风险或规范字段，只接收风险条目位置、处置结论和说明，
再从当前冻结载荷重建评价目标。保存结果带复核人 ID、时间、草稿版本、总评及逐项评价。
历史记录重新打开后可查看这些内容，同项目成员共享，跨项目不可见。

## 四、交互与失败路径

工作台下载区下方显示逐项评价表和复核总评：

1. 选择每条风险的评价结论；
2. 填写工程师说明；
3. 填写整份报告复核总评；
4. 接受草稿，或在有异议时退回/拒绝。

以下情况停止提交并明确报错：

- 接受时缺少任一风险评价；
- 接受时存在有异议条目；
- 评价位置不存在、重复或运行 revision 已变化；
- 草稿版本变化或文件指纹失效；
- 当前账号没有项目复核权限。

## 五、安全责任

工程师评价是报告草稿复核记录，不是正式预警发布、审核或签发。系统不得根据评价自动
降低风险等级，也不得将「未知」解释为安全。正式处置、预警和签发仍由工程责任流程完成。
