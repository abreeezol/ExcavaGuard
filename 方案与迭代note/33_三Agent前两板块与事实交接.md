# 三Agent前两板块与事实交接

日期：2026-11-04。保留三Agent主体，未推送上游。

## 展示逻辑

工程数据 → ①场景适配与判据匹配 → ②确定性计算、规则判级与事实冻结 → Supervisor → 报告Agent → 审计Agent → 工程师确认。

| 板块 | 回答什么 | 交付什么 |
|---|---|---|
| ①场景适配与判据匹配 | 当前工程按什么专业处理，使用哪些设置、规范范围与已确认补充规则 | 一次固定的工程上下文、适配器摘要、公共规范检索范围、项目规范及补充规则版本 |
| ②确定性计算、规则判级与事实冻结 | 本次算出什么、触发哪些规则、还有哪些缺项 | 所选报告周期事实、实际采用判据、辅助资料关联、来源文件、缺口、完整载荷摘要 |

公共规范目录表示后续RAG检索范围，不等于全部规范已转为数值规则；实际判级依据来自适配器已配置规则及工程师确认的项目规则。本文不代表隧道全部规范判据自动化已完成。

## 代码入口与复用

- 通用组织入口：`src/server/preparation/pipeline.ts`。
- 第一块：`prepareEngineeringScene`，项目绑定优先于请求中的设置，不从文件名推断工程；复用同一份专业能力及项目文档选择，减少重复读库。
- 第二块：`prepareEngineeringFacts`，调用已注册计算Skill、日报日期筛选Skill、项目规则Skill及辅助资料Skill，再生成摘要。
- 新增通用业务Skill：`prepare-engineering-facts`。专业计算、阈值、测项、模板仍在对应工程适配器，未搬入通用组织层。
- 原运行服务负责权限、输入文件授权、文件物化与清理、运行持久化，再将交接载荷传给原三Agent。

无需新增Agent，也没有引入LLM参与数值计算。原上传规范的三Agent变更审查流程继续保留；只有确认后的规则参与日常计算。

## 可靠性改进

1. 同一次运行固定工程设置、适配器和规则版本；计算开始和完成时核对专业能力与工程配置是否变化。变化则明确失败，要求重算，不混合不同版本，也不会把这种失败留成等待人工补参的无限循环。
2. 日报先利用完整时序计算，再筛选所选日期。修复基坑单份长表含多日数据时可能把基准日一起放入日报的问题；周报/月报/自定义区间继续复用原统计逻辑。
3. `project.pre_agent_preparation`记录两个板块的交接摘要，包括实际采用依据、未知/待核数量、输入文件SHA-256及完整载荷摘要。
4. `verifyPreparedFacts`在调用三Agent或续跑时校验完整交接载荷。数值、参数、规则、辅助资料等任何字段被改变都会阻断不一致交接；旧版本无此契约的历史载荷保持原兼容路径。
5. 模型上下文只传准备摘要中有助于分析的字段；不把哈希当正文事实，也不将判据对象数组变成不可读的`[object Object]`。引用仍使用真实冻结字段路径。
6. 结果页新增两个板块的简要展示，可展开实际采用依据和缺口，后台连接、数据库和哈希不作为日常用户填写项。
