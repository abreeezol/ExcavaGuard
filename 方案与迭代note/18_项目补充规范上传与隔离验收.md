# 项目补充规范上传与隔离验收

更新：2026-10-27。

## 使用方法

1. 在 `/workbench` 的“项目补充规范（全文检索）”区域，填写名称、带年份的标准编号、适用地区与本工程适用范围。
2. 选择20MB以内可搜索PDF或UTF-8 TXT/Markdown，核对文件效力及适用条件后勾选确认，点击上传。支持地方标准、行业标准及项目专项要求。
3. 查看页数、切片数、未完整入库页码及启用状态。相同编号重传新文件会停用旧来源；旧文件及历史引用保留。
4. 上传监测数据并生成日报/周期报告。新建运行默认采用当前工程启用规范；上传处理中运行按钮会禁用。历史记录续跑继续使用当时的冻结清单，重新加载输入新建运行则使用当前启用清单。
5. 检查报告具名规范依据、相关分类表备注、“多规范要求对照”“规范证据索引”“项目补充要求核查”。核查表的要求候选不代表已执行或已符合，须工程师确认。
6. 可停用不适用的补充规范，影响之后新建的运行；已有历史报告不追溯变化。

原“用户规范 JSON”仍用于人工确认的数值阈值及严格度比较。上传PDF不会自动覆盖数值阈值或改变风险等级；如PDF与冻结判据有差异，由工程师核对后通过该结构化入口补充判据。

## 数据位置与工程边界

原文件BLOB、元数据、切片和中文二元词FTS5索引全部位于独立数据库：

```text
var/project-standards/<project_id>/standards.sqlite3
```

可用 `EXCAVAGUARD_PROJECT_STANDARDS_ROOT` 更换专库存储根目录。公共Pinecone namespace、Chroma发布基线及默认阈值库均不写入。当前共享库语义检索不变，补充库使用本地FTS5/BM25；混合召回按库交替保留，不将BM25和向量分数直接比较。

项目标识只能从服务端会话取得；查询同时约束项目和冻结文档ID。相同文件上传至不同工程产生不同文档ID。单次最多50份补充文档，按编号只启用一个来源。

当前应用仍是单操作者单项目部署，`EXCAVAGUARD_PROJECT_ID` 为服务端工程UUID。不同工程必须配置不同UUID；只改页面工程名称不会切换工程，也不代表已实现多用户ACL。切换UUID后原会话失效。

即使监测文件和运行记录使用Supabase，规范专库仍位于本服务磁盘；部署时需要持久卷和备份。原文件不上传公共向量库；AI报告仍按现有模型配置发送本次相关条文候选及报告上下文。

## API与冻结链路

- `GET /api/project-standards`：当前工程规范元数据列表，不返回原文件BLOB。
- `POST /api/project-standards`：multipart `file`、`standard_name`、`standard_version`、`region`、`applicability`、`confirmed=true`。
- `PATCH /api/project-standards`：JSON `{ "document_id": "UUID", "active": false }`。不接受客户端指定project_id。
- `POST /api/runs`：可选 `project_standard_ids`；省略时当前工程全部启用文件，空数组时不选，显式列表只能引用本工程启用文档。
- 运行请求保存实际ID，结果保存包含SHA-256的 `project_standards` 元数据清单。执行器按冻结清单查询；停用和后续上传不会混入续跑。
- `provider=project` 证据包含标准名称、编号、条文号、页码、适用条件以及project_id/document_id/content_sha256。内部ID用于审计，前端及表格展示具名引用。
- AI模式在公共目录中加入当前工程规范，并继续逐规范与跨测项检索。正文必须引用每份命中的项目规范，否则有限重试后转人工；渲染器为对应分类表补充程序生成的核查候选。
- 模板模式不调用模型，只检索当前项目专库并保留补充核查结果，明确没有执行公共库运行时查询。

## 文件解析限制

本次“城市地下工程施工与运行监测技术规程.pdf”共107页，但特殊字体无法还原为可靠中文；pypdf输出大量`/G...`，备用解析器也产生控制字符。系统已增加拦截，拒绝把乱码当作正常全文入库。该文件需要先OCR成可搜索PDF或UTF-8文本，再通过前端上传。缺少文字层的扫描件同样明确拒绝，不自动声称检索完整。

PDF原文不自动纠正OCR错误，特别是数字与表格。候选条文仍须工程师核验，未命中不等于无要求。

## 本机验证环境

当前WSL使用 `.tools/node/bin/node`（Node24.13.0，运行时已gitignore）和 `.venv/bin/python`。若当前终端仍调用Windows的npm，请先在仓库执行 `export PATH="$PWD/.tools/node/bin:$PATH"`，再运行npm命令。Python需 `pypdf`、`fonttools`、`openpyxl`；均已在项目虚拟环境验证。

受限执行环境中的Vitest进程曾阻塞；在正常WSL环境以 `npm test -- --pool=threads --maxWorkers=1` 跑通全部回归。生产构建通过；现有Next.js16.4.0构建工具同时给出了安全升级提醒，本次未升级框架版本。
