**最终用途**

ExcavaGuard 的目标不是普通知识库问答，而是帮助基坑监测工程师把每日资料整理成一份**可复核、可追溯的监测日报草稿**。

完整链路会是：

1. 工程师上传当日监测 CSV 与施工工况记录。
2. 数据治理 Skill 解析字段、单位、方向、重复项和缺失项。
3. 规则引擎确定性计算累计变化、单次变化、变化速率，并依据已确认的项目规则判断异常。
4. 规范 RAG 检索适用条文，返回版本、条文号、原文、适用条件和证据 ID。
5. 存在异常时，案例检索与工况分析给出候选原因、反证、局限性和可信等级；证据不足就明确弃权。
6. 报告 Agent 根据结构化事实生成日报草稿。
7. 审计 Agent 校验数字、规则、引用、适用性和责任措辞，不通过则退回对应角色。
8. 工程师查看运行轨迹、证据和待确认项，修订后自行审核、发布或签发。

它的价值是让“日报里的数字、超限事实、规范依据、归因说明”能沿链路回溯，而不是让模型直接编写工程结论。

它不会自动发布预警、自动签字或替代工程师安全判断。

**是否需要 MCP**

核心项目**不需要 MCP**。你现在的 Next.js Route Handlers、Skill 脚本和 Supabase/Pinecone SDK 已经能完成 Web 主链路。

MCP 更适合作为后续适配层，例如：

- 让 WorkBuddy、Codex 或其他支持 MCP 的桌面 Agent 调用“导入数据”“查询运行轨迹”“读取证据”“生成草稿”等能力。
- 复用同一套 Skill 与规则，而不是为不同平台复制业务逻辑。
- 将来接入外部文档库、项目管理系统或工程文件系统时，统一工具调用协议。

建议顺序是：

`先完成 Web 主链路和 Skill → 再实现多 Agent 状态机 → 最后按展示需要暴露 MCP Server。`

这样 MCP 只是入口和适配层，不会变成系统核心依赖。
