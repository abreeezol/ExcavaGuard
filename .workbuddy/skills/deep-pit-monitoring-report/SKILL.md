# 深基坑监测日报生成

把已采集的监测数据加工成**可审核、可追溯的监测日报草稿**。核心立场：数值由脚本算、判定由规则给、文字由模型写、结论由工程师签。

## 硬性约束（任何步骤都不得违反）

0. **日报内容以 GB 50497-2019 第 9.0.7 条为准**：当日天气与工况、各测点本次测试值/单次变化值/变化速率/累计值、**巡视检查记录**、正常或异常的判断性结论、达到或超过预警值测点的**预警标示**及分析建议、其他说明，且宜采用附录 A~G 格式。缺任何一项都不算完成。
1. **不得手工推算数值**。累计量、本次变化量、变化速率、阈值比较一律由 `scripts/compute_metrics.py` 输出，禁止在对话中口算或让模型"顺便估一下"。报告中出现的每个数字都必须能在脚本输出的 JSON 里找到同值字段。
2. **依据必须有出处**。每条判定都要带 `依据` 字段：条款或项目规则名称 + 阈值来源文件。没有阈值配置的测项一律标 `待复核（阈值未配置）`，**禁止**用"经验值""通常按……"补阈值。
3. **信息不足时保留判断**。数据缺失、粗差存疑、案例匹配不足、工况记录缺失时，输出"尚不能判断，需补充：XXX"，不得生成确定性的原因解释。工况解释**只能补充**、**不能消除**超限标识。
4. **不越界**。只处理已有监测数据，不涉及现场采集；不替代责任单位出具正式监测报告；红色预警只做识别与提示，正式发布与处置按既有责任流程由人工确认。日报末尾必须保留该声明段。
5. **报告保留人工环节**。表尾"工程负责人 / 监测单位"、签署栏必须留空待填，不得代填人名或代为"已审核"；表头缺失字段（观测者、仪器编号、检定有效期等）留 `＿＿＿＿` 待填，**不得编造**。
6. **格式固定为 GB 50497-2019 附录表式**。日报按附录 A~G 的表式与字段生成，不得自行增删列、改列名或调换单位；表式之外的汇总信息只能放在"附表"章节并注明不属附录表式。

## 工作流

### 第 1 步：数据接入与校核

支持两种输入形态，先判别再走对应分支：

- **形态 ① 附录表式 Excel（优先）**：一个 `.xlsx` 文件中集中了按 GB 50497-2019 附录 A~G 表式整理的各表（每 sheet 一表，或单 sheet 多表）。表内累计量/本次变化量/变化速率已是填报值，**原样引用，不重新推算**；脚本只做表内一致性校核（高程差 vs 变化量、测值差 vs 本次变化）与分级判定。表头区（工程名称、观测者、仪器、监测时间等）与原表工况/分析文字自动提取。
- **形态 ② 观测流水 CSV**：每行一条观测记录。确认列含义：**测点编号、监测项目、观测日期、观测值/累计量、单位、初始值（若有）**，按 `references/field_mapping.md` 完成测点映射、单位归一（mm/cm 统一为 mm；**m、kN、kPa 等非位移量按原值保留不换算**）、日期清洗。

缺失值、格式异常、粗差由脚本识别并打标，**保留原始值，不静默剔除、不插值填补**。

- **形态 ③ 宽表高频累计数据（不符合附录表式）**：数据源是"首列时间戳 + 各测点一列累计量"的宽表（如盾构/监测系统的 10 分钟级连续导出，仅含累计量，无本次变化量/变化速率）。需用 `scripts/convert_wide_to_appendix_ab.py` 将其**总结整理**为 **GB 50497-2019 附录 A~G 中实际出现的附录**日报表格式（已覆盖：A 水平位移/竖向位移、B 深层水平位移、C 围护墙内力/立柱内力/土压力/孔隙水压力、D 支撑轴力/锚杆轴力、E 地下水位/地表竖向位移/分层竖向位移/坑底隆起、F 裂缝；G 巡视检查为定性表式；各附录表头块/列见 `scripts/appendix_forms.py` 与 `references/appendix_forms.md`）。脚本按确定性口径计算（非手工推算）：**累计变化 = 当日末次累计；本次变化量 = 当日末次累计 − 前一日末次累计；变化速率 = 本次变化量 / 报告间隔天数**；预警等级按 RAG 规则表（`references/rag_alarm_rules.json`，GB 50497-2019 表 8.0.4/8.0.5）对累计量占比判定（正常 <70%、黄色(需关注) 70%~100%、红色(报警) ≥100%）。**absolute 类**（位移/沉降/裂缝/水位）取规范绝对值；**design_ratio 类**（围护墙内力/立柱内力/土压力/孔隙水/支撑轴力/锚杆轴力）报警值=设计值×比例，需通过 `--point-design` 提供设计值，缺设计值则标"未判定"并注明表号（不写"需专项监测方案确认"）。宽表可含多个 sheet，脚本自动按点号前缀（A/B/C/D/E/F→对应附录）或 sheet 名关键词（深层/内力/轴力/水位/裂缝/巡视）归集。详见下方"宽表 → 附录 A~G 整理"小节。

### 第 2 步：确定性计算与判定（必须调用脚本）

形态 ①（附录表式 Excel，依赖 openpyxl）：

```bash
python scripts/parse_appendix_excel.py --excel <监测数据.xlsx> --config <阈值配置.json> --date <报告日期> --out result.json
```

形态 ②（CSV 流水）：

```bash
python scripts/compute_metrics.py --data <监测数据.csv> --config <阈值配置.json> --date <报告日期> --out result.json
```

两个脚本输出同一结构的 JSON，每个测点包含：`原始数据 / 计算结果 / 判定依据 / 状态标记` 四段，构成追溯链；形态 ① 另带 `表式`、`表头信息`、`按表式汇总`、`原表工况描述`、`巡视检查记录`。

注意：

- **阈值单位必须与数据列单位一致**。形态 ① 的列单位以附录表列头为准（表 E 变化量栏为 mm，即使高程栏为 m）；形态 ② 位移类统一换算为 mm。
- 形态 ① 是单期断面数据，**无时间序列，粗差识别不适用**；数据可靠性靠表内一致性校核与待复核标注。
- 阈值配置格式见 `references/thresholds.example.json`。**没有配置文件时**，用该文件拷一份骨架，把报警值留空，让脚本把所有测项标为待复核——先出草稿，再向用户要阈值，不要猜。

### 第 3 步：规范判据检索

按监测项目和判定结果检索适用依据，写入每条判定的 `依据` 字段：

- 优先用项目经审批的**专项监测方案**（阈值与分级的第一来源）；
- 其次是国家/地方标准（如 GB 50497-2019《建筑基坑工程监测技术标准》、地方基坑规程）；
- 需要原文时用 `gb-standard-pdf-fetch` skill 抓取官方全文 PDF，引条款号，不凭记忆写条款。
- 适用条件不明确或依据缺失 → 标记待复核，不得由模型补阈值。

### 第 4 步：工况比对与案例参照

结合开挖、支撑、降水、基准复测等工况记录解释变化原因。匹配充分则列出相似特征与案例来源；匹配不足注明参考范围；无法匹配明确提示信息不足。案例比对**不改变**第 2 步的超限判定。

### 第 5 步：成果生成（按 GB 50497-2019 附录表式）

**★ 标准交付物：监测日报「三件套」（本 skill 的默认、优先输出格式）**

生成监测日报时**固定产出以下三个文件**（一条命令，详见下方「监测日报（每附表一 sheet，标准形态）」小节）：

| 文件 | 内容 |
| --- | --- |
| `监测日报_<批次>_RAG.xlsx` | ①`监测日报`(封面)；②**每个出现的附录各占一个独立 sheet**（附表A~附表G 任意组合，用该附录原始表式渲染 + 表尾自动追加"简要分析及判断性结论"）；③`超限测点清单` |
| `监测日报_<批次>_RAG_封面.md` | **仅**「监测日报」封面 sheet 的内容（标题 / 工程信息 / 一、工况描述 / 二、简要分析及判断性结论 / 三、待复核事项 / 四、规范核对依据 / 五、签署） |
| `监测日报_<批次>_RAG_附表及清单.md` | 除封面外**其余 sheet**的内容（附表A~G 各表 + 超限测点清单） |

三份文件出自同一份 result JSON、内容一一对应：xlsx 便于归档/排版，两份 md 便于预览与纳入文档系统。参考样例：`examples/监测日报_附表AF_RAG.xlsx`（及两份同名 `.md`）。

> 仅当用户明确要"汇总式三 sheet 日报"（`render_workbook.py`）或"汇总页 + 附录逐表分页"（`render_summary.py`）时，才改用下方 C / A / B——那些是**并行可选产物**，不替代三件套。以下为其他可单独生成的成果：

**阈值/报警与"基坑智守 RAG 知识库"整合（推荐默认路径）**：数据阈值与报警判定以 RAG 知识库的报警值规则表为准（见 `references/rag_alarm_rules.json`，依托 RAG 已集成的 30 部规范，从 GB 50497-2019 表 8.0.4（基坑及支护结构监测预警值）、表 8.0.5（周边环境监测预警值）原文提取权威报警值；内力/轴力/土压力/孔隙水类按规范"报警值=设计值×比例"计）。在 `compute_metrics.py` / `parse_appendix_excel.py` 产出 result.json 后，用 `rejudge_by_rag.py` 整体重判，**不重算数值、不补阈值**：

```bash
python scripts/rejudge_by_rag.py --result result.json \
  --rules references/rag_alarm_rules.json --level 一级 --out result_rag.json
# 三级判定：正常 <70% 报警值；黄色(需关注) ≥70%；红色(报警) ≥报警值；规则表未覆盖项→未判定
# 之后用 result_rag.json 渲染 B/C 两份日报
```

RAG 规则表覆盖 **A~F 全部测项**：位移/沉降/裂缝/水位取规范绝对值（GB 50497-2019 表 8.0.4/8.0.5），围护墙内力/立柱内力/土压力/孔隙水压力/支撑轴力/锚杆轴力取"设计值×比例"；**缺设计值的 design_ratio 类**测点标"未判定"并注明表号，须补设计值后重判——不猜测阈值。

**C. 日报式监测 Excel 工作簿（.xlsx，按"监测日报"形态分 sheet，推荐在要出 Excel 时使用）**

```bash
python scripts/render_workbook.py --result result.json \
  --analysis 分析意见.json --meta meta.json --out 监测日报_YYYYMMDD.xlsx
```

输出单个 xlsx 工作簿，结构严格对应"监测日报_丰富版.md"：
- Sheet「监测日报」（首个工作表）：一、工况描述；二、简要分析及判断性结论（含判断性结论）；三、待复核事项；四、规范核对依据（仅列规范条款/表式/阈值来源，不展开逐点判定依据表）；五、签署栏（留空待签）；说明；
- Sheet「各类监测数据结果汇总」：按附录表式分类的汇总表（含合计行）；
- Sheet「超限测点清单」：预警信息清单（红/橙/黄排序，含"超限指标"列与判定理由，红预警底部加人工确认提示）。

即"监测日报"为第一个 sheet，"各类监测数据结果汇总""超限测点清单"为两个独立数据 sheet，**不展开表 A~F 逐表分页**（与日报形态一致）。数值全部原样引用同一份 result.json，可追溯。表头缺省自动取 result.json 的 `表头信息`，`--meta` 可覆盖。

**A. 监测数据汇总表（.xlsx，各类数据结果的汇总 + 表 A~F/表 G 逐表分页）**

```bash
python scripts/render_summary.py --result result.json \
  --analysis 分析意见.json --meta meta.json --out 监测数据汇总表_YYYYMMDD.xlsx
# 不需要巡视检查内容时加 --no-form-g（不生成表G sheet）
```

输出一个 xlsx：「汇总」页（按表式统计，**不再单列"表式"列**（表式并入"测项（所属表式）"）；超限测点清单含新增"超限指标"列说明达预警项（红/橙/黄底色分级）+ 待复核事项 + 工况描述 + 简要分析及判断性结论 + 编制/审核/签发留空栏）＋ 每个表式一页（附录表式表头表尾 + 主表）。表式以附录 A~G 为基准，**经项目确认的格式修改**仅三处并在汇总页"说明"中列明：①各表增加"预警等级"列；②表 B 增加"点号"列；③超限与待复核信息写入"备注"列并集中列示。表头字段缺省自动取形态 ① 提取的 `表头信息`，`--meta` 可覆盖。

**B. 监测日报草稿（.md，结构严格对应 C 项 Excel 工作簿）**

```bash
python scripts/render_report.py --result result.json \
  --analysis 分析意见.json --meta meta.json --out 监测日报_YYYYMMDD.md
# --meta 缺省时自动复用 result.json 的表头信息
```

文档结构与 C 项的 Excel 工作簿三 sheet 一一对应（不展开表 A~F 逐表详细报表）：
- 第一节「监测日报」：一、工况描述；二、简要分析及判断性结论（含判断性结论）；三、待复核事项；四、规范核对依据（仅列规范条款/表式/阈值来源，无逐点判定依据表）；五、签署栏（留空待签）；说明；
- 第二节「各类监测数据结果汇总」（无序号前缀）：按附录表式分类汇总表，含合计行；
- 第三节「超限测点清单」（无序号前缀）：预警信息，按红/橙/黄排序，含"超限指标"列说明是累计量/变化速率/控制值中哪一项达到预警，并附判定理由。
数值全部原样引用同一份 result.json，可追溯。

表式与字段以 `references/appendix_forms.md` 为准（来源：GB 50497-2019 附录 A~G，规范 PDF 见 `references/`）。按测项自动归入对应表式，**一张表只出现该表式适用的测项**：

| 表式 | 适用测项 | 主表列（固定，不得增删改） |
| --- | --- | --- |
| 表 A | 水平位移、竖向位移 | 点号｜累计位移量(mm)｜本次变化量(mm)｜变化速率(mm/d)｜备注 |
| 表 B | 深层水平位移（测斜） | 深度(m)｜累计位移(mm)｜本次变化量(mm)｜变化速率(mm/d)（右侧留曲线位） |
| 表 C | 内力、土压力、孔隙水压力 | 组号｜点号｜深度(m)｜本次测值｜上次测值｜本次变化｜累计变化(kPa)｜备注 |
| 表 D | 支撑轴力、锚杆轴力 | 组号｜点号｜深度(m)｜本次测值｜上次测值｜本次变化｜累计变化(kN)｜备注 |
| 表 E | 地下水位、地表竖向位移、分层竖向位移、坑底隆起 | 编号｜点号｜初始高程(m)｜本次高程(m)｜上次高程(m)｜本次变化量(mm)｜累计变化量(mm)｜变化速率(mm/d)｜备注 |
| 表 F | 裂缝 | 点号｜长度(4 列)｜宽度(4 列)｜形态（需分项数据，缺项留 — 并说明） |
| 表 G | 巡视检查 | 分类｜巡视检查内容｜巡视检查结果｜备注（29 项固定清单；结果由现场巡视人员填写，脚本只出空表式，若 `--analysis` 的 `巡视检查` 字段提供了记录则按内容填入） |

各表固定表头：第（　）次、工程名称/报表编号/天气、观测者/计算者/校核者、仪器型号/仪器编号/检定有效期、本次监测时间/上次监测时间；表内下部固定"**工况描述**"与"**简要分析及判断性结论**"；表尾固定"工程负责人 / 监测单位"与"第 　 页 共 　 页"。表头由 `--meta` 传入（`meta.json` 字段：工程名称、报表编号、天气、观测者、计算者、校核者、仪器型号、仪器编号、检定有效期、本次监测时间、上次监测时间、序号）。

附录表式**没有"超限/待复核"列**，故这类标识写入各表"备注"列（xlsx 各表式分页）；日报"汇总表"的"二、超限测点清单"与"三、待复核事项"章节已集中列示预警信息与待复核事项。

`--analysis` 传入分析意见 JSON，结构如下（文字由模型依据**已核定结果**撰写，不得引入新数值）：

```json
{
  "工况描述": "当日开挖/支撑/降水/基准复测情况（写入每张表的工况描述栏）",
  "总体分析": "挂数据与依据的分析文字",
  "结论": "判断性结论；信息不足处写明尚不能判断与需补充内容",
  "表式分析": { "表A": { "工况描述": "该表专属工况", "简要分析及判断性结论": "该表专属分析" } },
  "测点分析": { "ZCL-01": { "工况解释": "", "依据": "条款或方案表号", "案例": "", "证据充分": true } }
}
```

`表式分析` 可选：给某张表写专属的工况描述与分析；缺省则该表沿用全局文字。`测点分析` 用于逐测点解释，`证据充分: false` 的测点标注"不足，保留判断"。

未提供 `--analysis` 时，相关段落留 `【待填写】` 占位，不代写结论。

生成后**先跑自动自检**，再按 `references/self_check.md` 逐条人工自检：

```bash
python scripts/validate_report.py --report 监测日报_YYYYMMDD.md --result result.json \
  --config thresholds.json --out 自检结果.md
```

自动自检必须"表格数值一致性"通过、且第 2 节清单为空（或逐条说明为何属正常例外，例如工况描述中的人工数字）；未通过不得交付。随后按 `references/self_check.md` 人工核对：数值—结论一致性、字段完整性、依据可追溯、待复核已标注。任一不过关，回到对应步骤重做，不得直接交付。

## 宽表高频累计数据 → 附录 A~G 日报表整理（形态 ③）

把不符合附录表式的宽表累计数据整理为规范日报表（覆盖附录 A~G；当前已支持 A 水平位移、B 深层水平位移、C 围护墙内力等、D 支撑轴力等、E 地下水位等、F 裂缝，G 巡视为定性表式）：

```bash
# 单个宽表输入
python scripts/convert_wide_to_appendix_ab.py \
  --excel examples/附表AB_测试数据_10分钟_一周.xlsx \
  --rules references/rag_alarm_rules.json \
  --level 1 \
  --point-alarm examples/point_alarm_sample.json \
  --point-design examples/point_design_sample.json \
  --out examples/附表AB_转换日报表.xlsx \
  --out-json examples/附表AB_转换_result.json

# 多个宽表输入（典型场景：已有 A/B 数据，后续又给出 C~F 数据）
# → 合并输出到**同一个工作簿**，附表 A~F 各自一个 sheet，格式与单个输入时完全一致
python scripts/convert_wide_to_appendix_ab.py \
  --excel examples/附表AB_测试数据_10分钟_一周.xlsx examples/附表CDEF_测试数据.xlsx \
  --rules references/rag_alarm_rules.json \
  --level 1 \
  --point-design examples/附表CDEF_测试数据_design.json \
  --out examples/附表AF_转换日报表.xlsx \
  --out-json examples/附表AF_转换_result.json
```

> 注意：`--level` 取 **1/2/3**（整数，默认 1=一级），不要写成"一级"等中文。

- **多文件合并**：`--excel` 可同时传入多个 xlsx，脚本按测点编号合并（同点号以样本更多的人为准），所有附录仍然输出在**同一个工作簿**中、各自成 sheet。这样即便 A/B 与 C~F 来自不同数据文件，也能得到一份包含 `附表A`~`附表F` 的完整日报表。

- 输入：宽表 xlsx（首列时间戳 + 每列一个测点的"累计位移量(mm)"，仅含累计量）。可含多个 sheet，脚本自动扫描并归集。
- `--level`：基坑安全等级（1/2/3，默认一级），决定 RAG 报警值；也可改用 `--point-alarm point→报警值(mm)` JSON 逐点覆盖（如浅基础二级 50 mm、深基础一级 30 mm，见 `examples/point_alarm_sample.json`），`--point-rate` 同理覆盖速率报警值。
- 计算口径（确定性、由脚本算，非手工推算）：累计位移量 = 当日末次累计；本次变化量 = 当日末次累计 − 前一日末次累计（首日为当日末−当日首）；变化速率(mm/d) = 本次变化量 / 报告间隔天数（间隔取前后采样日期差，通常 1d）。
- 输出工作簿：每个实际出现的附录一个「附表X_…监测日报表」sheet（A~G 任意，例如 `附表A_水平位移监测日报表`、`附表C_围护墙内力等监测日报表`、`附表D_支撑轴力等监测日报表`、`附表E_地下水位等监测日报表`、`附表F_裂缝监测日报表`），每个 sheet 采用该附录原始表式（表头块 第（）次/工程名称/观测者/仪器型号/本次监测时间/上次监测时间 + 浅蓝列头 + 预警等级按红/黄/绿底色写入备注格 + 表尾 工况描述/简要分析/工程负责人/监测单位/页码）；最后附一个 `处理与判定说明` sheet（输入形态、计算方法、阈值来源、点号→报警值(设计值)映射、各附表预警统计、声明）。各附录列与表头以 `references/appendix_forms.md` / `scripts/appendix_forms.py` 为准。注：附录 B 原数据无分层深度时深度列填"—"并在说明注明需核对原始记录；附录 C/D 的"本次测值/上次测值"由累计序列端点推算（注明于备注）。
- 预警等级按累计位移量占报警值比例：正常 <70%；黄色(需关注) 70%~100%；红色(报警) ≥100%；变化速率单独比对并在备注提示，等级以累计量为准，速率独立报警须项目专项监测方案确认（不臆造）。红色仅识别提示，正式发布按责任流程人工确认；表头/签署栏留空待填。
- `--out-json` 输出每个数字的计算结果（供 `validate_report.py` 自检数值一致性）。
- 若要把宽表结果直接渲染为"汇总页 + 附录 A~G 逐表分页"形态的监测数据汇总表（即 `render_summary.py` 的产物），用 `scripts/convert_result_to_summary_json.py` 把上一步的 `--out-json` 结果桥接一次即可：`python scripts/convert_result_to_summary_json.py --result <转换_result.json> --out <桥接_result.json>` → `python scripts/render_summary.py --result <桥接_result.json> --out 监测数据汇总表_完整.xlsx`（默认含表 G 空巡视表式；不需要表 G 时加 `--no-form-g`）。桥接时取每个测点末次监测日值，三级判定（正常/需关注/报警）映射为 render_summary 四级（正常/黄色/红色），C/D/E/F 的"本次测值/高程"等原始值宽表未提供则标"—"。

## 监测日报（每附表一 sheet，标准形态）— 调用 RAG 模型做阈值判定（附录 A~G）

> **★ 本 skill 的标准输出格式（已固化）**：生成监测日报固定产出**三件套**——
> - ① `监测日报_<批次>_RAG.xlsx`：`监测日报`(封面) + **每个出现的附录各占一个独立 sheet**（附表A~附表G 任意组合，用该附录原始表式渲染，表尾后自动追加"简要分析及判断性结论"） + `超限测点清单`；
> - ② `监测日报_<批次>_RAG_封面.md`：**仅**封面 sheet 内容；
> - ③ `监测日报_<批次>_RAG_附表及清单.md`：除封面外**其余 sheet**内容。
>
> 参考样例：`examples/监测日报_附表AF_RAG.xlsx`、`examples/监测日报_附表AF_RAG_封面.md`、`examples/监测日报_附表AF_RAG_附表及清单.md`。这是本 skill 生成监测日报的**标准形态**（区别于 `render_workbook.py` 的"汇总式三 sheet"——那是并行可选产物）。

基于 `convert_wide_to_appendix_ab.py` 产出的 result JSON（键为 `附表A`/`附表B`/…，动态识别实际出现的附录），做阈值判定并生成上述形态监测日报：

```bash
# 生成日报 xlsx（每附表一 sheet），并同时导出两份 Markdown
python scripts/gen_daily_report_rag.py --result 附表AF_转换_result.json \
  --out 监测日报_附表AF_RAG.xlsx --md
```

- **输出（一条命令全出）**：①`监测日报_附表AF_RAG.xlsx`（每附表一 sheet 的日报）②`..._封面.md` —— **仅**「监测日报」封面 sheet 的内容 ③`..._附表及清单.md` —— 除封面外其余 sheet（附表 A~G + 超限测点清单）的内容。Markdown 由 `scripts/export_daily_report_md.py` 从 xlsx 忠实镜像导出（封面结构化、表式 sheet 转 Markdown 表格），可单独调用：`python scripts/export_daily_report_md.py --xlsx 监测日报_附表AF_RAG.xlsx`（`--cover-sheet` 指定封面 sheet 名，`--out-cover/--out-rest` 自定义输出路径）。
- **RAG 检索为可选增强、非硬依赖**：脚本先尝试 `import` RAG 项目 `source/report_core.py` 并调用 `kb_search()` 对**各出现的监测项目**及"表 8.0.4 报警值基准"发起向量检索（本地 `bge-small-zh` + `chroma_db` 集合 `jikeng_norms`），命中 GB 50497-2019 表 8.0.4/8.0.5、JGJ120-2012、GB 50007 等权威条款，作为"四、规范核对依据"的引用来源（含 score/来源/条款号/摘录）。**若 RAG 项目或向量库未就位，自动回退到 `references/rag_alarm_rules.json` 内嵌的 GB 50497-2019 表 8.0.4/8.0.5 规范出处**，日报仍可稳定生成且依据可追溯——本期实测两种路径均可产出。
- 阈值判定：对每点末次监测日累计位移量按各点报警值做 70%/100% 三级判定（正常 <70% / 需关注 70%~100% / 报警 ≥100%）；`超限测点清单` 的"规范依据"列直接取该测点 `rule_key` 在规则表中的规范出处（绝对准确，不依赖 RAG）。
- 输出单个 xlsx 工作簿（默认 `监测日报_附表AB_RAG.xlsx`，可按 `--out` 指定；可同时用 `--result` 指向其他附录的 result JSON）：①`监测日报`（一、工况描述；二、简要分析及判断性结论；三、待复核事项；四、规范核对依据（RAG 检索引用）；五、签署栏留空）；②**各出现的附录独立 sheet**（如 附录A 水平位移 / 附录B 深层水平位移 / 附录C 围护墙内力等 / 附录D 支撑轴力等 / 附录E 地下水位等 / 附录F 裂缝 全序列日报表，每个 sheet 采用该附录原始表式 + 表尾后自动追加"简要分析及判断性结论"，预警等级红/黄/绿底色）；③`超限测点清单`（末次监测日需关注/报警测点，含规范依据列）。
- 同时输出 `*_RAG_result.json`（含 RAG 检索命中/规则出处、各点判定、统计、综合判定），供追溯。
- 依赖：基础仅 `openpyxl`；**RAG 检索为可选**——启用真实条款检索需 `chromadb`/`sentence-transformers`/`torch`（CPU 版即可）且 RAG 项目 `chroma_db` 与 `bge-small-zh` 就位（脚本 `RAG_SRC` 常量指向 RAG 项目 `source/`，跨设备改为环境变量/同步路径）；缺则自动回退规则表出处。
- 红色预警仅作识别提示，正式发布按责任流程人工确认；表头/签署栏留空待填。

## 依赖

- 形态 ②（CSV）全流程仅用 Python 标准库。
- 形态 ①（附录表式 Excel）与汇总表 xlsx 输出依赖 `openpyxl`（`pip install openpyxl`），缺失时脚本会明确报错退出，不会静默降级。
- 调用 RAG 模型检索阈值（`gen_daily_report_rag.py`）额外依赖 `chromadb`/`sentence-transformers`/`torch`（CPU 版即可，`pip install chromadb sentence-transformers torch`），且需 RAG 知识库项目已构建的 `data/chroma_db` 向量库与本地 `models/bge-small-zh` 模型；脚本通过 `RAG_SRC` 常量指向 RAG 项目 `source/` 目录，跨设备使用时需同步该路径或改为环境变量。
- `examples/` 内有两种形态的完整示例与复跑说明（`示例监测数据_附录表式.xlsx`、`示例监测数据.csv` 等）。

## 部署与跨设备使用（分发）

本 skill 目录自包含（除 `requirements.txt` 声明的 `openpyxl` 外无外部依赖），靠目录扫描被 Agent 自动发现，**无需注册/安装步骤**。迁移到别的电脑或设备时：

1. **搬运目录**：把整个 `deep-pit-monitoring-report/` 文件夹复制到目标机的以下任一位置（二者等价，按范围选）：
   - 用户级（所有项目可用）：`~/.workbuddy/skills/deep-pit-monitoring-report/`
   - 项目级（随项目仓库走，协作者克隆即得）：`<项目根>/.workbuddy/skills/deep-pit-monitoring-report/`
   - 推荐用 **Git 仓库**托管该文件夹（或整个 `.workbuddy/skills/`），多设备 `git clone`/`git pull` 即同步；也可直接 zip 拷贝。注意 `references/` 内的规范 PDF 约 25MB，会一并带上。
2. **装依赖**：在目标机用 Agent 的 Python 运行 `python -m pip install -r requirements.txt`（只需形态①/xlsx 时必装 `openpyxl`；纯 CSV 形态可跳过）。
3. **调用方式**：启动 WorkBuddy 后，Agent 会在用户请求匹配"基坑监测/监测日报/汇总表/超限测点"等意图时自动加载本 skill；也可在对话中显式点名 `deep-pit-monitoring-report`。SKILL.md 中的命令统一用 `python scripts/xxx.py`（由 Agent 运行时解析），**不要写死本机 venv 绝对路径**，以保证跨设备可跑。
4. **集成进专用 Agent**：若想做一个"基坑监测日报"专用 Agent，可借助 `expert-manager` skill 把本 skill 封装为专家/专家包；或直接在专项 Agent 的系统提示里要求"优先加载 deep-pit-monitoring-report skill"。通用 Agent 下无需额外配置，靠自动发现即可。
